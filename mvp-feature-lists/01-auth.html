۱. چهار حالت کاربری — تعریف شفاف

در ویراشاپس هویت یک‌بار ساخته می‌شود. نقش‌ها روی همان حساب سوار می‌شوند. بازدیدکننده حساب ندارد؛ سه نقش دیگر همگی User احراز‌شده هستند.

VISITOR

بازدیدکننده

وارد نشده. می‌تواند کاتالوگ، جستجو و صفحات عمومی را ببیند. برای Cart پایدار، Checkout، سفارش و پنل‌ها باید با موبایل + OTP وارد شود.

USER

کاربر / خریدار

حساب شخصی دارد. خرید B2C و (در صورت واجد شرایط بودن) B2B، سبد، سفارش، پرداخت و پروفایل خودش.

SELLER

فروشنده

همان User است به‌علاوه پروفایل فروشنده. به Seller Panel و منابع متعلق به خودش دسترسی دارد؛ به فروشنده دیگر نه.

ADMIN

مدیر

حساب داخلی سیستم. از UI عمومی ساخته نمی‌شود. مدیریت کاربران، فروشندگان، محصولات، سفارش‌ها و تنظیمات.

مدل هویت (یک جمله)

شناسه ورود شماره موبایل یکتا است. Visitor = no session. User / Seller / Admin = یک User + Role، همه با همان OTP موبایل وارد می‌شوند. فروشنده سیستم ورود جدا ندارد. ایمیل اگر در پروفایل باشد فقط تماس است، نه Login.

سؤال Visitor User Seller Admin
حساب در دیتابیس دارد؟ خیر بله بله + Seller Profile بله
ورود لازم است؟ خیر موبایل + OTP موبایل + OTP موبایل + OTP
ثبت‌نام از UI عمومی؟ شماره → OTP → حساب جدید اگر شماره جدید باشد ارتقا به فروشنده بعد از ورود خیر — شماره Admin داخلی seed می‌شود
مقصد بعد از ورود — فروشگاه / حساب Seller Panel Admin Panel
مرجع کنترل دسترسی فقط API عمومی Backend — نه Frontend

۳. فیچرهای غیرفنی (کسب‌وکار و تجربه کاربر)

آنچه کاربر روی صفحه می‌بیند و محصول باید انجام دهد — بدون جزئیات پیاده‌سازی.

Visitor

بازدیدکننده

  • ورود به سایت بدون ساخت حساب
  • دیدن دکمه ورود با موبایل
  • وارد کردن شماره موبایل و درخواست کد
  • وارد کردن OTP دریافتی از پیامک
  • اگر شماره جدید باشد: حساب خریدار ساخته می‌شود
  • اگر شماره از قبل باشد: وارد همان حساب می‌شود
  • ارسال مجدد کد با شمارش معکوس
  • در Checkout: هدایت به ورود با موبایل
  • ندیدن پنل فروشنده و پنل ادمین
User

کاربر / خریدار

  • ورود و ثبت‌نام با یک جریان: موبایل + OTP
  • ماندن در حساب تا خروج
  • خروج آگاهانه
  • دیدن پروفایل خودش (شماره موبایل قابل مشاهده، تغییر شماره جداگانه و نیازمند OTP جدید است)
  • ویرایش فیلدهای مجاز پروفایل — ایمیل اگر باشد فقط تماس است، نه ورود
  • دیدن وضعیت حساب (فعال / غیرفعال / …)
  • پیام خطای قابل فهم برای شماره نامعتبر، کد غلط، یا کد منقضی — بدون افشای جزئیات داخلی
  • بعد از ورود، ادامه همان کاری که می‌خواست (مثلاً برگشت به سبد)
Seller

فروشنده

  • درخواست / ثبت‌نام فروشنده (متصل به حساب)
  • ورود با همان شماره موبایل + OTP به Seller Panel
  • دیدن پروفایل فروشنده و اطلاعات کسب‌وکار خودش
  • اگر وضعیت Pending است: ورود ممکن، دسترسی عملیاتی محدود، پیام وضعیت واضح
  • اگر Suspended / Inactive: عدم دسترسی به پنل عملیاتی
  • ندیدن داده و پنل فروشنده دیگر
  • خروج از پنل
Admin

مدیر

  • ورود به Admin Panel با موبایل + OTP — نه از مسیر ثبت‌نام فروشگاه
  • دیدن لیست کاربران و وضعیت حساب‌ها
  • فعال / غیرفعال کردن حساب در محدوده MVP
  • تأیید یا تغییر وضعیت فروشنده (Pending → Active / Suspended)
  • عدم نمایش OTP، توکن و secret در هیچ صفحه‌ای
  • خروج از پنل مدیریت

۴. فیچرهای فنی

۴.۱ لایه‌ها (طبق SRS-01)

Authentication Layer

  • Request OTP (ارسال پیامک)
  • Verify OTP → Login یا ایجاد User
  • Resend OTP با rate limit
  • Logout / invalidate token
  • اعتبارسنجی Authentication روی هر درخواست محافظت‌شده
  • اتصال User به درخواست (req.user)
  • رد درخواست بدون توکن/سشن معتبر با 401 Unauthorized

Account Layer

  • Create user
  • Retrieve user (فقط خود / ادمین)
  • Update permitted profile fields
  • Account status handling
  • شناسه یکتا: شماره موبایل

Authorization Layer

  • Role identification: USER / SELLER / ADMIN
  • Permission check قبل از هر عمل محافظت‌شده
  • 403 Forbidden اگر نقش کافی نیست
  • Seller isolation: فقط داده خودش
  • منبع حقیقت Permission فقط Backend است

API / Contract

  • tRPC برای فرانت Next.js
  • Validation در مرز Presentation (Zod / DTO)
  • Error response استاندارد و i18n
  • عدم برگرداندن OTP، hash، secret، توکن داخلی
  • Procedureهای دقیق بعد از نهایی شدن API Contract

۴.۲ تصمیم فنی قطعی — Phone OTP

موضوعMVPتوضیح
روش ورود شماره موبایل + OTP پیامکی ایمیل و رمز عبور برای Authentication استفاده نمی‌شوند. یک جریان برای ورود و ثبت‌نام.
شناسه حساب شماره موبایل نرمال‌شده و یکتا BR-01 Unique Account. فرمت ایران (مثلاً 09xxxxxxxxx) در Validation قطعی می‌شود.
ثبت‌نام ضمنی: اولین OTP موفق روی شماره جدید → ساخت User با Role=USER فرم جداگانه ایمیل/رمز وجود ندارد. تکمیل پروفایل بعد از ورود است.
OTP تولید در Backend، ذخیره موقت در Redis، ارسال SMS OTP در دیتابیس User ذخیره نمی‌شود. بعد از تأیید یا انقضا حذف می‌شود.
Session JWT Access Token؛ Redis برای OTP و در صورت نیاز blacklist TokenServiceAdapter موجود است.
رمز عبور وجود ندارد PasswordHasher برای Login استفاده نمی‌شود. bcrypt در کد فعلی ربطی به این جریان ندارد.
ایمیل اختیاری در پروفایل — نه شناسه ورود Email adapter می‌تواند برای اعلان بماند؛ Auth به آن وابسته نیست.
Admin seed اولین Admin با شماره موبایل seed می‌شود — نه Register عمومی همان OTP؛ نقش از قبل ADMIN است.
ماژول دامنه src/modules/users سایر ماژول‌ها Role را از اینجا می‌گیرند.

۴.۴ خطاهای فنی که باید پوشش داده شوند

Invalid Phone · Invalid OTP · OTP Expired · OTP Rate Limited · Unauthorized · Forbidden · Resource Not Found · Server Error · SMS Delivery Failure

پیام خطا OTP صحیح را لو نمی‌دهد و بین «شماره جدید» و «شماره موجود» در مرحله ارسال کد تمایز امنیتی غیرضروری ایجاد نمی‌کند — هر دو مسیر کد می‌گیرند؛ بعد از Verify اگر User نبود ساخته می‌شود.

۴.۵ تست اجباری (DoD)

  • Unit: نرمال‌سازی موبایل، صدور/تأیید/انقضای OTP، ساخت User روی شماره جدید، قوانین Role
  • Integration: Redis OTP، SMS adapter، ذخیره‌سازی User، جریان Authentication
  • E2E: شماره جدید → OTP → حساب ساخته شد → دسترسی به Account
  • E2E: شماره موجود → OTP → ورود به همان حساب
  • E2E منفی: OTP غلط / منقضی → عدم ورود · درخواست بدون Token → Access Denied

۵. جریان‌های اصلی

A. ورود / ثبت‌نام با OTP (یک جریان)

Visitor شماره موبایل را وارد می‌کند← Validation فرمت شماره← Rate limit بررسی می‌شود← Backend OTP می‌سازد و در Redis می‌گذارد← SMS ارسال می‌شود← کاربر کد را وارد می‌کند

B. تأیید OTP

Verify کد + شماره← رد اگر غلط / منقضی / مصرف‌شده← اگر User نیست → ساخت با Role=USER← اگر هست → بررسی Status حساب← حذف OTP از Redis← صدور Token · مسیر بر اساس Role

C. دسترسی محافظت‌شده

درخواست + Token← Authenticate در Backend← Authorize Role/Permission← اجرای Use Case← 401 یا 403 در شکست

D. فروشنده

User با OTP موبایل وارد می‌شود← ایجاد Seller Profile · Status=Pending← Admin وضعیت را Active می‌کند← دسترسی Seller Panel و محصولات/سفارش‌های خودش

۸. خارج از اسکوپ MVP این ماژول

عمداً ساخته نمی‌شود تا Scope باد نکند. معماری نباید بسته شدن مسیر آینده را سخت کند.

  • ورود با ایمیل یا رمز عبور
  • بازیابی رمز عبور (رمز وجود ندارد)
  • تأیید ایمیل به‌عنوان شرط ورود
  • Advanced IAM · Enterprise SSO · چند OAuth Provider
  • Biometric · Risk Engine · AI Identity · Trust Score · Fraud Detection پیشرفته
  • RBAC/ABAC پیچیده فراتر از نقش‌های پایه
  • Multi-tenant Enterprise Identity
  • ۲FA اجباری با TOTP اپلیکیشن — OTP پیامکی همان روش ورود است، نه لایه دوم

۱۰. تصمیم‌هایی که قبل از پیاده‌سازی باید قطعی شوند

روش ورود قطعی است: موبایل + OTP. موارد زیر هنوز باید در Technical Design / Figma ثبت شوند:

  1. طول OTP، مدت اعتبار، و فاصله ارسال مجدد
  2. سقف تلاش غلط قبل از قفل موقت
  3. ارائه‌دهنده SMS و رفتار خطای ارسال پیامک
  4. نرمال‌سازی شماره ایران (با/بدون +98)
  5. مدل دقیق Session / Token (مدت اعتبار، Refresh، Logout)
  6. فیلدهای پروفایل بعد از ورود مطابق Figma — نه فیلدهای Login
  7. نقش‌های دقیق MVP و Permission هر نقش
  8. سیاست Account Status (چه وضعیتی OTP را می‌پذیرد ولی پنل را می‌بندد)
  9. آیا یک نفر هم‌زمان خریدار و فروشنده است (پیشنهاد: بله، یک User چند Role)
  10. API Contract نهایی tRPC برای requestOtp / verifyOtp / logout / me
