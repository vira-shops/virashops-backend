ماژول سفارش

تبدیل سبد معتبر به Order با Snapshot قیمت، شماره یکتا، وضعیت مستقل از Payment، تاریخچه خریدار، دید فروشنده فقط روی اقلام خودش، و مدیریت ادمین با مجوز. B2B سیستم سفارش موازی ندارد. درگاه و secret پرداخت در ماژول Payment است.

زنجیره: Product → Cart → Order → Payment → Fulfillment. انتقال وضعیت آزاد نیست. Overselling با تراکنش/قفل موجودی در Backend جلوگیری می‌شود — جزئیات Lock با CTO. Checkout مهمان تا تأیید PO ساخته نمی‌شود.

۱. چهار حالت کاربری — Order

VISITOR

بازدیدکننده

سفارش ندارد. Checkout بدون OTP ممنوع. مهمانِ پرداخت‌کننده خارج از MVP تا PO.

USER

کاربر / خریدار

Checkout از سبد خودش، ایجاد Order، پرداخت از ماژول Payment، تاریخچه و جزئیات و وضعیت. فقط buyerId = self.

SELLER

فروشنده

سبد را مدیریت نمی‌کند. سفارش‌هایی که قلم محصول خودش را دارند می‌بیند. تغییر وضعیت فقط در محدوده مجاز PO.

ADMIN

مدیر

جزئیات سفارش، مشتری، فروشنده، وضعیت سفارش/پرداخت/تحویل. تغییر وضعیت با Permission. از پنل خرید نمی‌کند.

وضعیت سفارش MVP (SRS-07)

Pending → Payment Pending → Paid → Processing → Preparing → Shipped → Delivered به‌علاوه Cancelled و Failed. مسیر دقیق Cancellation / Refund با Business Rule نهایی — حدس زده نشود.

Payment Status جداست: Unpaid / Pending / Paid / Failed / Refunded / Partially Refunded — منطق کامل در SRS-08.

۳. فیچرهای غیرفنی

خریدار

تجربه سفارش

  • مرور سبد و مبلغ سرور در Checkout
  • وارد کردن تحویل مطابق Figma
  • رفتن به درگاه از Payment — نتیجه موفق/ناموفق/در انتظار
  • لیست سفارش‌ها و صفحه جزئیات با نشان وضعیت
  • B2B: همان صفحات؛ پیام خطای MOQ اگر تعداد غلط باشد
فروشنده / ادمین

عملیات

  • فروشنده: سفارش اقلام خودش، بدون سبد مشتری و بدون داده رقیب
  • ادمین: جستجو/فیلتر/صفحه سفارش‌ها
  • تغییر وضعیت با تأیید UI برای لغو/شکست
  • ندیدن کلید درگاه

۴. فیچرهای فنی

Domain · orders

  • جدا از carts و payments
  • State machine؛ Transition نامعتبر = DomainError
  • OrderItem با snapshot نه FK زنده قیمت
  • ایجاد از use case Cart.validate سپس Order.create
  • Cross-module: صدا زدن use case نه import entity کاتالوگ

API

  • Create Order
  • Get Order · List customer orders
  • Get status · Cancel اگر مجاز
  • Seller list own · Admin list all + pagination

یکپارچگی و امنیت

  • Atomic create: Order ناقص نماند؛ موجودی بی‌کنترل کم نشود
  • Index: customerId, orderNumber, status, createdAt, seller روی item
  • لاگ بدون داده کارت/توکن درگاه
  • IDOR: 403 بدون افشا

تست DoD

  • Unit: شماره یکتا، transition، snapshot، جمع‌ها
  • Integration: Cart→Order، موجودی همزمان
  • E2E: سبد → Checkout → Order → (mock payment)
  • منفی: سفارش User دیگر؛ قیمت جعلی؛ سبد خالی

۵. جریان‌های اصلی

A. ایجاد سفارش

سبد معتبر← Checkout + تحویل← Re-validate stock/price← Transaction: Order + Items + number← Payment intent← اعلان Created

B. پرداخت (مرز Payment)

وضعیت Payment جدا← موفق → Paid + ادامه پردازش← ناموفق → Failed قابل نمایش

C. دید فروشنده

سفارش ثبت شد← فیلتر قلم‌های sellerId=self← وضعیت در محدوده PO
