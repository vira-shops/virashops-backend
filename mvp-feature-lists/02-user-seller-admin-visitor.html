۲. چهار بازیگر — تعریف شفاف

هویت یک‌بار ساخته می‌شود. نقش‌ها روی همان حساب سوار می‌شوند. بازدیدکننده حساب ندارد. User و Seller و Admin همگی User احرازشده‌اند؛ تفاوت در Role، پروفایل فروشنده، و سطح پنل است.

VISITOR

بازدیدکننده

وارد نشده. کاتالوگ، جستجو، دسته و جزئیات محصول عمومی. پنل‌ها قفل. Checkout و سفارش فقط بعد از OTP. سبد مهمان نهایی نشده (SRS-04).

USER

کاربر / خریدار

ثبت‌نام با موبایل + OTP. پروفایل، خرید B2C، در صورت واجد شرایط B2B، سبد، پرداخت، تاریخچه سفارش، اعلان سفارش/پرداخت. همان هویت می‌تواند بعداً فروشنده شود.

SELLER

فروشنده

User + پروفایل فروشنده. ثبت‌نام/ارتقا، اطلاعات کسب‌وکار، وضعیت Pending / Active / Suspended / Inactive. پنل: داشبورد پایه، محصول و سفارش خودش. ایزوله از فروشنده دیگر.

ADMIN

مدیر

حساب داخلی؛ ثبت‌نام عمومی ندارد. پنل: داشبورد، کاربران، فروشندگان، محصولات، سفارش‌ها، دسته‌ها، محتوای MVP، تنظیمات، Audit. از پنل ادمین خرید نمی‌کند.

مدل هویت (یک جمله)

شناسه ورود شماره موبایل یکتا است. Visitor = no session. User / Seller / Admin = یک User + Role، همه با همان OTP موبایل. فروشنده سیستم ورود جدا ندارد. ایمیل هرگز Login نیست. تغییر شماره — اگر در MVP باشد — OTP جدید روی شماره جدید می‌خواهد؛ جزئیات در 01-auth.html و تأیید PO.

۳. فصل بازدیدکننده · Visitor

VIS-* بدون حساب. فقط سطح عمومی فروشگاه. هر عمل حساب/خرید/پنل یعنی هدایت به OTP یا Deny.

۳.۱ تعریف شفاف

بازدیدکننده کسی است که Session معتبر ندارد. می‌تواند ویترین را ببیند تا تصمیم بگیرد وارد شود. نمی‌تواند به حساب، سبد پایدار قطعی، Checkout، سفارش، پرداخت، Seller Panel یا Admin Panel دسترسی پیدا کند — مگر بعد از تبدیل شدن به User با OTP.

۳.۴ فیچرهای فنی

سطح دسترسی

  • Queryهای عمومی: دسته فعال، محصول Published، جستجو، محتوا
  • هیچ req.user لازم نیست
  • Mutation سبد پایدار / سفارش / پرداخت → 401
  • مسیر /seller و /admin → Deny در فرانت و بک‌اند

قواعد داده

  • فیلتر انتشار فقط در Backend؛ فرانت منبع حقیقت نیست
  • قیمت نمایش‌داده‌شده از سرور است
  • موجودی انبار داخلی و داده فروشنده دیگر افشا نمی‌شود
  • OTP: همان قرارداد 01-auth — بدون ساخت Admin از این مسیر

خطا

  • Not Found برای محصول نامعتبر یا unpublished (بدون افشای دلیل داخلی)
  • Empty results برای جستجو
  • Validation شماره موبایل روی فرم OTP
  • Rate limit پیام قابل‌فهم

تست DoD

  • Unit: فقط Published در query کاتالوگ
  • HTTP: GET عمومی ۲۰۰؛ POST سفارش بدون توکن ۴۰۱
  • E2E: مرور → جزئیات → CTA ورود
  • منفی: حدس URL پنل ادمین

۳.۸ خارج از اسکوپ این بازیگر

  • حساب، پروفایل، تاریخچه، اعلان شخصی
  • ورود ایمیل/رمز، OAuth، مهمانِ پرداخت‌کننده بدون OTP (تا PO)
  • دیدن پیش‌نویس فروشنده یا سفارش دیگران
  • قیمت عمده — مگر PO نمایش عمومی را بخواهد

۳.۹ تصمیم‌های باز بازدیدکننده

  1. آیا سبد مهمان در MVP هست؟ محلی است یا سروری؟ بعد از OTP چطور Merge می‌شود؟
  2. Checkout مهمان (SRS-04 تصریح کرده نهایی نشده).
  3. آیا بازدیدکننده نام فروشگاه را روی کارت می‌بیند؟
  4. نمایش موجودی عددی یا فقط «موجود / ناموجود»؟

۴. فصل کاربر / خریدار · User

USR-* خریدار ثبت‌شده با موبایل + OTP. مالک حساب، سبد، سفارش و پرداخت خودش. می‌تواند بعداً Seller شود.

۴.۱ تعریف شفاف

User همان خریدار B2C است. هویت با شماره موبایل یکتا ساخته می‌شود (شماره جدید → حساب جدید با نقش USER؛ شماره موجود → ورود به همان حساب). ایمیل در پروفایل اگر باشد فقط تماس است. اگر واجد شرایط B2B باشد، همان سبد و همان زنجیره سفارش — سیستم سفارش موازی ندارد.

۴.۴ فیچرهای فنی

Account / Auth

  • Create user روی OTP موفق شماره جدید
  • Login روی OTP موفق شماره موجود
  • Retrieve / update profile فقط self (یا Admin)

  • ایمیل unique اختیاری اگر ذخیره شود — نه کلید Auth

Commerce

  • Invalid OTP / expired / rate limit — بدون enumeration
  • Unauthorized · Forbidden · Not Found
  • Insufficient stock · MOQ not met · Invalid qty
  • Payment failed قابل نمایش، بدون secret درگاه

تست DoD

  • Unit: قوانین تعداد، موجودی، MOQ، قیمت سرور

۵.۱ تعریف شفاف

فروشنده حساب جدا نمی‌سازد: روی User موجود (یا بعد از OTP شماره جدید) پروفایل Seller ساخته می‌شود. فیلدهای ثبت‌نام SRS-02: نام، موبایل، ایمیل اختیاری، اطلاعات کسب‌وکار، نام فروشگاه. وضعیت: Pending · Active · Suspended · Inactive.   • Conflict وضعیت غیرمجاز (مثلاً انتقال نامعتبر سفارش)
  • Not Found منابع حذف‌شده

تست DoD

  • Unit: انتقال وضعیت User/Seller/Product/Order
  • Integration: pagination و فیلتر
  • E2E: seed Admin → OTP → تغییر وضعیت Seller → Audit ثبت شد
  • منفی: User عادی به procedure ادمین → 403؛ Register عمومی Admin نمی‌سازد

۶.۹ تصمیم‌های باز مدیر

  1. ماتریس نهایی RBAC و اینکه Super Admin در MVP هست یا یک نقش Admin کافی است.
  2. آیا همان شماره می‌تواند هم Admin باشد هم خریدار فروشگاه؟
  3. UI لاگ Audit در MVP یا فقط ذخیره بک‌اند؟
  4. مدت نشست ادمین کوتاه‌تر از خریدار؟
  5. ایجاد محصول توسط Admin «در صورت نیاز» — چه کیس‌هایی؟
  6. سطح مجاز دیدن تاریخچه سفارش کاربر تا کجاست (اقلام، پرداخت، آدرس)؟

۷. تصمیم‌های باز مشترک — قبل از پیاده‌سازی حدس زده نشود

SRS صریحاً می‌گوید Developer این‌ها را بدون تأیید Product Owner / CTO فرض نکند. جزئیات مکانیک OTP در 01-auth.html است؛ اینجا فقط تقاطع بازیگران.

  1. سبد و Checkout مهمان: SRS-04 مرور مهمان را مجاز دانسته؛ Checkout مهمان را نهایی نکرده. VIS-12 / VIS-13.
  2. وضعیت Rejected فروشنده: در SRS-09 هست، در فهرست وضعیت SRS-02 نیست. PO/CTO.
  3. نقش‌های ادمین: پنج نقش نمونه SRS-09 نهایی نیستند.
  4. واجد شرایط B2B: چه کسی قیمت عمده را می‌بیند — فلگ روی User، آستانه خرید، یا تأیید دستی؟
  5. نمایش عمده به Visitor: پیشنهاد این سند: خیر.
  6. سبد چندفروشنده: یک سفارش Marketplace یا چند سفارش per seller؟
  7. چه کسی Publish می‌کند: Seller مستقیم یا Admin بعد از Pending Review؟
  8. انتقال وضعیت سفارش: کدام را User می‌بیند، کدام را Seller عوض می‌کند، کدام فقط Admin.
  9. رزرو موجودی: add-to-cart یا Checkout.
  10. Admin و خریدار روی یک شماره: مجاز یا ممنوع.
  11. فیلدهای Figma پروفایل، Checkout، ثبت‌نام فروشنده.
  12. کانال اعلان برای USR-13 و SLR-13 (SMS در OTP قطعی است؛ بقیه نه).
  13. سیاست Account Status برای Login و خرید.
  14. قرارداد tRPC نهایی per actor — این سند قابلیت است نه schema.

Auth جزئیات OTP را جدا نگه می‌دارد. این فایل را با 01-auth.html با هم بخوانید. اگر آن سند هنوز ردی از ایمیل+رمز در بخش فنی قدیمی داشته باشد، این سند و تصمیم Product ملاک بازیگران است: Phone OTP only.
