ماژول محصول و کاتالوگ

لیست شفاف فیچرهای Catalog برای Visitor · User · Seller · Admin. Backend منبع حقیقت قیمت، موجودی و انتشار است. مشتری فقط محصول منتشرشده را می‌بیند؛ فروشنده فقط محصول خودش را می‌سازد.

منبعSRS-03 + SRS-04 (افزودن به سبد) + SRS-05 (شرایط عمده روی محصول) + SRS-09 (وضعیت پنل ادمین)
خروجیفیچر غیرفنی + فنی + ماتریس نقش‌ها · شناسه PRD-*
وضعیت Implementationماژول Products هنوز ساخته نشده؛ MinIO/S3 برای تصویر آماده است

نحوه خواندن وضعیت فیچر: در اسکوپ SRS تأییدشده در SRS-03 — پیشنهادی MVP لازم، ولی جزئیات به PO/CTO واگذار شده — زیرساخت آماده در بک‌اند فعلی وجود دارد — خارج از MVP عمداً ساخته نمی‌شود. Variant پیشرفته، PIM و AI Catalog وارد این سند به‌عنوان تعهد نمی‌شوند.

۱. چهار حالت کاربری — Catalog

هویت از 01-auth.html می‌آید. این ماژول فقط کالا، دسته، قیمت، موجودی، تصویر و انتشار را مالک است. جستجوی عمومی در 04-search.html است؛ افزودن به سبد در 05-cart.html.

VISITOR

بازدیدکننده

فقط محصول منتشرشده: عنوان، تصاویر، قیمت خرد، موجودی قابل‌نمایش. Draft / Inactive را نمی‌بیند. افزودن پایدار به سبد بعد از OTP است مگر PO سبد مهمان را تأیید کند.

USER

کاربر / خریدار

همان ویترین + انتخاب تعداد و افزودن به سبد. اگر واجد شرایط B2B باشد قیمت عمده و MOQ روی همین محصول — نه کاتالوگ موازی.

SELLER

فروشنده

ساخت / ویرایش / لیست محصول خودش. قیمت، موجودی، تصویر، دسته، شرایط عمده. ایزوله از فروشنده دیگر. انتشار نهایی ممکن است نیازمند Admin باشد (PO).

ADMIN

مدیر

مشاهده و مدیریت همه محصولات. کنترل انتشار، غیرفعال‌سازی نامعتبر، دسته، اتصال به فروشنده. از پنل ادمین خرید نمی‌کند.

سؤالVisitorUserSellerAdmin
چه محصولی می‌بیند؟ فقط Published / Active قابل‌فروش همان + خرید همه وضعیت‌های خودش همه فروشندگان و وضعیت‌ها
ایجاد / ویرایش؟ — — فقط مالک همه · در صورت نیاز ایجاد
قیمت عمده؟ پیشنهاد: خیر اگر واجد شرایط تنظیم روی محصول خودش نظارت صحت
منبع قیمت / موجودی Backend — کلاینت منبع حقیقت نیست

۳. فیچرهای غیرفنی

Visitor / User

ویترین

  • لیست محصول منتشرشده با تصویر، نام، قیمت خرد
  • صفحه جزئیات: توضیحات، گالری، موجودی به‌زبان انسان
  • خریدار: انتخاب تعداد و «افزودن به سبد»
  • ناموجود: محصول دیده می‌شود، خرید قفل — الگوی دقیق با Figma
  • قیمت عمده به بازدیدکننده نشان داده نمی‌شود مگر PO خلاف بگوید
Seller

پنل کالا

  • فرم ایجاد: نام، دسته، توضیحات، قیمت، موجودی، تصاویر
  • ویرایش همان فیلدها روی محصول خودش
  • لیست با تصویر بندانگشتی، قیمت، موجودی، وضعیت، تاریخ به‌روزرسانی
  • شرایط عمده روی همان فرم محصول
  • پیام واضح اگر Pending Review یا Inactive است
Admin

کنترل پلتفرم

  • لیست همه محصولات با جستجو و فیلتر وضعیت / فروشنده / دسته
  • انتشار یا برداشتن از ویترین
  • غیرفعال‌سازی کالای نامعتبر
  • در صورت نیاز اصلاح اطلاعات
  • ایجاد محصول «در صورت نیاز» — کیس را PO مشخص می‌کند

صفحات UI

  • لیست عمومی / جزئیات عمومی — SRS-03 / 04
  • Seller: List · Add · Edit · Images · Price · Inventory · Status
  • Admin: Products list / edit / publish — SRS-09
  • فیلدهای دقیق فرم با Figma قفل می‌شود

۴. فیچرهای فنی

۴.۱ لایه‌ها

Domain

  • ماژول products — موجودیت غنی، نه TypeORM در دامنه
  • وضعیت و Transition کنترل‌شده
  • قیمت و موجودی invariant در مدل
  • مالکیت sellerId غیرقابل جعل از کلاینت
  • دسته از use case ماژول Category؛ import entity دسته ممنوع

Use cases

  • Create / Update / Get / List / Search (پنل)
  • Update price / Update stock
  • Upload / Remove / Set primary image
  • Publish / Unpublish / Deactivate
  • Public catalog query: فقط قابل‌نمایش

Persistence / Files

  • Product · ProductImage · Inventory · (Price اگر جدا)
  • فایل در MinIO/S3 — هرگز در Postgres
  • Index روی sellerId، categoryId، status، updatedAt
  • Pagination سروری اجباری

API / امنیت

  • tRPC برای Next.js؛ Validation در مرز
  • عمومی: list/detail Published بدون توکن
  • Seller mutation: Role + ownership
  • رد Price / Stock از Client به‌عنوان حقیقت
  • عدم افشای موجودی داخلی انبار یا داده فروشنده دیگر

۴.۳ خطا

Product Not Found · Unauthorized · Forbidden (مالک دیگر) · Invalid Product Data · Invalid Category · Invalid Price · Insufficient Stock · Invalid Image · Upload Failed · Product Already Inactive · Seller Not Sellable

محصول unpublished برای مشتری مثل Not Found است — بدون افشای Draft بودن.

۴.۴ تست DoD

  • Unit: Validation، Transition وضعیت، Publish rules، مالکیت، قیمت سرور
  • Integration: Postgres + S3 تصویر؛ اتصال Seller و Category
  • Authorization: Seller A به محصول Seller B → 403
  • Edge: Stock=0 · Price=0 · بدون تصویر · دسته حذف‌شده · Seller غیرفعال · Quantity > Stock
  • E2E: Seller Active → ایجاد → Publish (طبق PO) → Visitor می‌بیند · Inactive از ویترین حذف

۵. جریان‌های اصلی

A. ایجاد توسط فروشنده

Seller Active وارد پنل← فرم کالا← دسته + قیمت + موجودی + تصویر← Validation Backend← وضعیت اولیه MVP (معمولاً Draft)

B. انتشار

شروط Publish← Seller یا Admin طبق PO← Active + قابل‌نمایش← ویترین Visitor/User و ایندکس جستجو

C. مصرف خریدار

لیست / جزئیات Published← قیمت و موجودی از سرور← افزودن به سبد اگر User← در Order: Snapshot نه قیمت زنده بعدی

۱۰. تصمیم‌هایی که قبل از پیاده‌سازی حدس زده نشود

  5. تخفیف روی محصول در MVP فعال است؟
  6. سقف نوع/حجم/تعداد تصویر
  7. Variant: صفر در MVP یا رنگ/سایز ساده؟
  8. ایجاد محصول توسط Admin — چه کیس‌هایی؟
